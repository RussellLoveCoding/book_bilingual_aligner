#### Fix #2：md 附录的**裸行子节标题**（`tools/bil/txtimport.py`）

**病象**：中文 md 的附录里，子节标题是**没有 `#` 前缀的裸行**：

```
A.1 柯尔莫哥洛夫概率系统        ← 裸行，无 # 无粗体
```

`_MD_HEAD_RE`（要有 `#`）和 `_bare_head`（≤12 字、且必须全长匹配 `_ZH_HEAD_RE`）
**两条都不认** → 整个附录被解析成 **1 个 section**（中文 88 段 vs 英文 6 节）。
这正是 §6.16 (2) A 类「附录整章未译」的**真身**。

**修法**：新增一个**只认附录子节**的裸行判据，命中后**在当前文档内**追加
一个 `level=2` 的 heading 块（**不开新文档**）：

```python
_APX_SUBHEAD_RE = re.compile(r"^([A-Z])\.(\d{1,2})(?:\.\d{1,2})?\s+\S")

def _bare_subhead(line: str, lang: str) -> str:
    """裸**子节**标题（附录 A.1 / B.3 …）。命中返回标题文本，否则空串。"""
    if lang != "zh":
        return ""
    t = (line or "").strip()
    if not t or len(t) > 60:
        return ""
    if not _APX_SUBHEAD_RE.match(t):
        return ""
    if t.endswith((".", "。", ",", "，", ";", "；", ":", "：")):
        return ""
    return t
```

⚠ **为什么不用「加进 `_ZH_HEAD_RE`」**：那会把 `###` 级也判成章、把单元切碎
（§6.6 已经警告过）。这里必须**只做 heading 块、不开新单元**。

### 6.26 ★★★ 第五把尺子 `dbg_drift.py`（语义漂移）+ 「散落公式图」根因（2026-09-18 16:xx）

> 用户本轮原话：「你复盘一下我这几天提到的问题……**你能评估出来吗？我看你好像每次
> 评估不出来? 改完之后每次都说行，结果每次都不行**」。并给了 14 张截图

> 上一章节的注释里头；实例：第八章末尾/第九章前面」。
>
> **本轮纪律：先造尺子、不修对齐、不宣布任何「修好了」。**

#### ① 为什么「每次说行、结果不行」—— 四条根因（本轮的正面回答）

1. **我的四把尺子全是形式判据**（标记泄漏 / 前缀 / 同侧粘连 / 对内顺序 /
   公式守恒），都不需要理解内容。用户报的五类缺陷（漏译 / 漂移 / 张冠李戴 /
   倒置 / 英文没有的中文有）里 **4 类是语义判据**——你得知道「这段中文翻的是
   不是这段英文」。**形式全绿 ≠ 语义正确，两把尺子在量不同的东西。**
2. **没有金标准**（定调 #1 一直没落实）。没有 ground truth 就没有召回率，
   我只能验证「我刚修的那一个 case」，验证不了「同类还剩多少」。
3. **修机制、验个案**。fm-title / `_head_block` / `_bare_head` / 白名单……
   每次找到的是「一种」机制，修完只验那一个。同一症状（漂移）有 N 种机制，
   **我从没量过 N 是多少**。
4. **今天第一版漂移尺子自己就是证据**：`w:`（长拉丁词）当跨语言信号 →
   报 504 条，抽样 **8/8 假警报**（`Bernoulli`→「伯努利」音译）。
   ——「尺子没先验证」这个错误我今天又犯了一次。

#### ② 漂移尺子：`tools/dbg_drift.py`（零 LLM，秒级）

原理：抽「跨语言必然保留」的信号做**邻域反查**（±`--win`，默认 2）。

    DRIFT    EN 的编号/公式号，本对 ZH 没有，但邻格 ZH 有  ⇒ 译文落在邻格
    MISATTR  ZH 的编号/公式号，本对 EN 没有，但邻格 EN 有  ⇒ 中文挂错英文
    SKEW     长度比（汉字/英文词）偏离本章中位数 ±60%   ⇒ 弱信号

**信号有效性是实测出来的，两个坑都踩过：**

| 信号 | 结论 | 证据 |
|---|---|---|
| `word`（长拉丁词/专名） | **不可用**，精密度 ≈ 0 | 504 条 DRIFT 抽样 8/8 假警报，全是音译 |
| `num` 分隔符只认 `.` | **假警报** | 原版 `Fig. 4.2` ↔ 中译本「图4-2」用**连字符**，8 条全误报 |
| `num` 尾部断言 `(?![\d.])` | **假警报** | 「练习4.6。」句号把 4.6 整条挡掉 |
| `eq`（括号公式号） | **可用**（曾误判不可用） | 偏移直方图 **99% 是 +0.00**（671 样本）——中译本公式号与原版**同号**，我从 2 个样本下结论「不同号」被数据推翻 |
| `int`（≥2 位整数） | **未验证**，默认关 | 153+125 条，没抽样 |

⇒ **默认 `--sig num,eq`**。用法：
`bash _run.sh dbg_drift.py <成品.html> [--audit] [--list drift|misattr|skew] [--doc chNN]`

#### ③ 实测结果（`diag/prob_p7/`，全书 6172 pair）

读者看到：**英文标题 → 中文标题 → 中文正文 → 英文正文**。
中文标题被夹在英文标题和自己的中文正文之间 —— 标题与正文脱节。
这就是「标题中文对齐错误」。截图对比见
`.workbuddy/tmp/real_prob_p4.png`（错）vs `real_prob_p5.png`（对）。

#### ② 根因：同一个 xhtml 里存在**两种顺序约定**

| 位置 | 谁在发 | 次序 |
|---|---|---|
| `.pair` **内部** | `_reorder_pairs(zh_first=True)`（build.py:2556） | **zh 先、en 后** |
| **标题** h2/h3/h4 | `_head_block()`（build.py:436） | **en 先、zh 后** ← 相反 |

`_reorder_pairs` 只重排 `<div class="pair">` 的子树；**标题在 pair 之外**，
从没被它碰过。而 `_head_block` 里的两个 `if` 顺序是 en 在前、zh 在后。

为什么 CSS 救不了：`ORDER_CSS` 的 `.ord-zh .pair > .zh { order: 1 }` 是
**后代选择器挂在 `.pair` 上**，标题不是 `.pair` 的子元素 ⇒ 规则不生效。
即 **DOM 顺序就是阅读器看到的顺序**（这也是 `_reorder_pairs` 存在的原因）。

#### ③ ★★★ 为什么三把尺子全绿 —— 判据正交

| 尺子 | 量的是什么 | 为什么不报 |
|---|---|---|
| `dbg_qa.py` ① | 「≥3 个同侧长段连成坨」 | zh/en **完美交替**，一个同侧串都没有 |

是**尺子覆盖面**问题 —— 与 §6.20、§6.22、§6.23 是同一类错误的第 3、4 次复发。

### 6.23 ★★★ 题注（caption）三连缺陷 —— 尺子「测不出」的第二种形态（2026-09-18 14:0x）

#### ① 根因：`_is_caption_text` 对英文题注**系统性失明**

`build.py` 旧正则（已删，注释里留了原文备查）：

```python
_CAP_TEXT_RE = r"^\s*(?:表|图|Table|Figure)\s*\d+(?:\s*[-–—]\s*\d+)?\s*$"
               r"|^\s*(?:表|Table)\s*\d+[-–—]\d+"
```

**两条分支都要求「破折号」衔接编号**（`Table 29-1`），而这本书英文原版用的是**点号**：
`Table 3.1.` / `Table 8.2.`。⇒ 全书 **16 个英文题注 0 个命中**，
而中文侧的 `表 3-1 …`（破折号）却命中 13 个。

**两侧识别能力不对称 ⇒ 题注在 EN 侧当正文、在 ZH 侧当题注 ⇒ 一切配对/宽度决策全偏。**

#### ② 连带两个缺陷（一个是尺子，一个是产线）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| a | EN 题注**从不带 `caption` 类** | `render_chapter` 的 EN 分支只按块类型出 class，唯一判题注的地方 `_is_caption_text(_zplain)` 判的是**中文** | EN 题注渲染成普通正文（不居中/不小字） |
| b | ZH 题注 class 只有 `caption`，**丢了 `zh` token** | 两处 `parts.append(...)` | ①`.zh` 的宋体族 + `font-weight:500` 丢失；②`.ord-*` 的 `.pair > .zh` 重排规则认不出它；③**`dbg_order` 侧别判据把它当「无侧别」→ 误报成「仅英文段」** |

#### ③ 修法与 `_V` 决策

新实现（`build.py`）：`_CAP_KEY` / `_CAP_NUM` 拆开，
`_CAP_HEAD_RE` 认 `表|图|Table|Figure` + `\d+[.\-–—]\d+`，
**点号与破折号等价**。另加三条排除：
- `_CAP_PROSE_RE` —— 编号后紧跟**小写英文词**（`Table 3.1 lists the results…`）⇒ 是正文引用，不是题注
- `_CAP_EQREF_RE` —— 数句数前先挖掉 `(15.34)`，**公式编号里的点号不是句子边界**
- `_CAP_SUB_RE` —— `(a)`/`（甲）` 小标题多句也放行
判据：长度 ≤110、正文句数 <2（除非有子标题）、正文长度 ≤70。

**`_V` 保持 15**（**不 bump**）。理由：改动落在
（i）**渲染层** `build.py` —— 无缓存；
（ii）`pipeline.looks_like_zh_title` —— pipeline 无缓存。
`fastcache` 的三个用户里，`epubparse.py` 不调 `_is_caption_text`，
`sectmine.py` / `titlesrc.py` 也不调。⇒ **bump 只会白白作废整份解析缓存，不换任何正确性。**

### 6.21 ★★ 序言~第二章的「标题对齐错」= 解析器丢了 `fm-title*` 卷头标题（2026-09-18 13:5x）

用户点名范围：「**序言部分到第二章**」的 ①中英段落倒置 ②**标题对齐错误**。
本节把 ② 查到根因（① 见 §6.20 ②）。

#### ① 根因：英文原版卷头标题的 class 是 `fm-title*`，解析器**一个都不认**

英文 epub 里卷头标题长这样（`prob_en.epub`）：

```html
<p class="fm-title2"><a id="page_xvii"/>Preface</p>          ← 08_fm-chapter1.html
<p class="fm-title2"><a id="page_xvii"/>Editor’s foreword</p> ← 07_fm-chapter.html
<p class="fm-title2">Contents</p>                             ← 06_toc.html
<p class="fm-title">PROBABILITY THEORY</p>                    ← 02_half-title.html
<p class="fm-title1">THE LOGIC OF SCIENCE</p>                 ← 02_half-title.html
```

`_semantic_type()`（`epubparse.py:375`）判 heading 的两条路**都不匹配**：

| 判据 | 正则 | `fm-title2` 为什么不过 |
|---|---|---|
| `_CLASS_HEAD_RE` | `(?:^\|[\s_-])h([1-6])(?:[a-z])?(?:[\s_-]\|$)` | 类名里**没有 `hN`** |
| `_CLASS_TITLE_RE` | `(?:chapter\|section\|part)[\s_-]?title` | **没有 chapter/section/part 前缀** |

⇒ 落到 `return "para"` —— **卷头标题被当成正文段**。

**中文侧却是有标题的**（`prob_zh.md` 里是 raw markdown `### 前言` / `### 编者序`），
⇒ **英文少一个标题、中文有一个** ⇒ 该标题起的小节配对**整体左偏一格**。
这正是用户看到的「标题中文对其错误」。

#### ② 量：全书只有 **5 处** `fm-title*`，全是卷头

```
[fm-title2] Contents
[fm-title2] Editor’s foreword
[fm-title]  PROBABILITY THEORY
[fm-title1] THE LOGIC OF SCIENCE
[fm-title2] Preface          ← 用户报的「前言」
```

**零副作用**：其余 1782+ 个无 class 的 `p`、1418 个 `para`、1315 个 `noindent1`
**都不受影响**（它们不匹配 `fm-title` 任何形态）。

#### ③ 拟修（**已离线验证，尚未落库**）

在 `_semantic_type` 里加第三条判据（与另两条并列，仍要过
`_looks_like_heading` 兜底）：

```python
_CLASS_FM_TITLE_RE = re.compile(
    r"(?:^|[\s_-])fm[\s_-]?title\d*(?:[\s_-]|$)", re.I)
```

离线验证结果（`_semantic_type` 直接调用）：

| class | text | 现判 | 修判 |
|---|---|---|---|
| `fm-title2` | Preface | para | **heading** |
| `fm-title2` | Editor's foreword | para | **heading** |
| `fm-title2` | Contents | para | **heading** |
| `fm-title` | PROBABILITY THEORY | para | **heading** |

### §6.35 泛化机制：DP 不确定 → LLM 语义裁决（2026-09-18 21:5x）

> **用户定调（本节的缘起）**：「以后翻译其他电子书，会不会又不行。程序设计最大的
> 能力是能够泛化，其中就是在**确定性算法不起作用的时候，利用 LLM 的能力来补齐**。
> 你现在的感觉好像是给我调参 DP …… 日后迁移到其他电子书，可能会出现其他的问题。」
> 「要是调参和针对性修改，没法应用到更好地识别其他电子书，那就完蛋了。」
> 「注意 LLM 判决的高效和缓存命中，设计 LLM 的输入要简洁、输出也要，这样高效也省钱。
> 我的 LLM 模型是 `qwen3.7-flash`，太过复杂的它不会，因为用其他模型贵，所以你要
> 设计好提示词和如何提问 LLM。」

#### ① 机制三件套（`align` + `llm` + `pipeline`）

| 环节 | 函数 | 职责 |
|---|---|---|
| 找疑点 | `align.probe_uncertain_zh(a_paras, b_paras, k)` | k 次采样跑 DP，找**处置不稳定**的中文段（A 摇摆）+ **稳定独有**段（B） |
| 定上下文 | `align.judge_windows(...)` | 用 DP 配对结构定位每个候选的上下文窗口（英文侧前后各若干段） |
| 判块级 | `llm.judge_zh_blocks(...)` | 逐块二元问答，**只输出单字符 `Y`/`N`**（成本最低、flash 模型友好） |

        and en_figs                                  # 闸门② 必须有图（§6.36 加）

**语义依据只有一个**：英文原版把某段写成了**图/公式**，中文译本写成了**散文** →
粒度天然对不上 → 该中文段应当丢弃（用户 2026-09-18 定调）。**没有图就没有这个

#### ⑤ ★ 伪标题的泛化判据（把「词表」换成「结构性信号」）

**泛化判据（零词表、跨书成立）**：短中文段紧跟公式时，**看英文侧在同一位置

_EN_TERMINAL_RE = re.compile(r"[.!?:;。！？：；][\"'”’)\]]*\s*$")

def _en_looks_like_running_prose(t: str) -> bool:
    s = " ".join((t or "").split())
    if len(s) <= 60 or " " not in s:

    return not _EN_TERMINAL_RE.search(s)

### §6.37 补译幻觉的根因与修复：AI 补译出「22. 传播理论导论」（2026-09-18 23:xx）

#### ① 现象（用户截图）

公式 (22.70) 附近，AI 补译条目标着「22. 传播理论导论」—— 书中根本没有这章。

#### ② 根因

英文原版里那段是 `<p class="noindent1">and in</p>` —— 一句被**公式图劈开**后掉下的
两词残片。中文版把这两词并进了下一段，于是这一小段在 DP 眼里成了「en-only」（只有
英文、没有对应中文）→ 走补译分支 → 把两个孤零零的词 `and in` 丢给 LLM，
LLM 只能**凭空编**一个书名来交差。

这是「补译」这条路的**系统性漏洞**：它假设「en-only 段都有可翻译内容」，
但被图表/公式劈碎的残片恰恰**没有**。

#### ③ 修法：`pipeline._too_short_to_translate(t)`

判据（零词表、跨书成立）：

* ≤2 个词 **且** 无句末标点（`.?!:;。？！：；`）→ 判定为残片，不发给 LLM；
* **豁免**：含 `, 123` 形态的**索引条目**（`Aristotle, 4`）—— 那是「词 + 页码」，
  补译有意义，不该误伤。

```python
_FILL_MIN_WORDS = 3
_INDEX_ENTRY_RE = re.compile(r"[,，]\s*\d+")

def _too_short_to_translate(t: str) -> bool:
    s = " ".join((t or "").split())
    if not s:
        return True
    if s.endswith((".", "?", "!", ":", "。", "？", "！", "：", ";")):
        return False
    if _INDEX_ENTRY_RE.search(s):
        return False
    return len(s.split()) < _FILL_MIN_WORDS
```

补译循环里跳过并如实打印跳过数（不静默）：

```
[补译] 跳过 27 个「≤2 词的残片」（无可译内容，防幻觉）
```

### §6.38 【调研】公式超链接在微信读书的弹窗 vs 跳转（2026-09-18 23:xx，结论：**只能跳转**）

#### ① 现状

我们当前公式引用的实现（`build.py:_link_refs_by_eqno` / `_link_eq_refs`）：

```html
<a class="eqref" href="#eq-4491f8b5ecc0">(1.1)</a>   <!-- 正文引用 -->
...
<table class="eqtable" id="eq-4491f8b5ecc0">…<td class="eqno">(1.1)</td></tr></table>
```

**纯标准锚点跳转**，全书 1824 处 `eqref` / 1745 张 `eqtable`。微信读书里点一下
就是**页面跳转**到公式所在位置（用户实测）。

#### ② 用户的类推：注释能弹窗，公式为什么不能？

注释能弹窗是因为它**换成了一套阅读器认得的私有标记**（多看系）：
`build.py` 里 `_note_entry` 把注释放进 `<aside epub:type="footnote">`，
注标处挂 `class="noteref duokan-footnote"`（`build.py:_rewrite`）、
再加微信书城同款 `<img class="qqreader-footnote" alt="注N：全文">`。
三条路都指向**注释内容**，微信读书认其中一条就会弹。

#### ③ 调研结论：公式引用**做不到**弹窗，原因在「弹窗内容从哪来」

微信读书（及所有支持弹窗的阅读器）弹窗的本质是——
**主文里挂一个小标记，弹窗正文另存在一个「可弹出容器」里**，标记用锚点指过去。
对照多看的规范（`launchpad.net/bugs/2130478` 转录的多看弹窗注格式）：

```html
<!-- 正文里的标记 -->
<a class="duokan-footnote" href="#df-1"><img src="../Images/note.png"/></a>
<!-- 文末/章末集中存放，不进正文流 -->
<ol class="duokan-footnote-content">
    <li class="duokan-footnote-item" id="df-1"><p>这是一个注释文本。</p></li>
</ol>
```

**关键点**：弹窗依赖「**另有一份独立于正文流的文本**」。
注释天然满足 —— 注释条目本来就在章末注区，是**文本**。

而公式**没有这样一份文本**。读者点 `(1.32)` 想看的是什么？是**那张公式图**。
我们的公式是 `<img class="eqimg" src="…">`（1745 张，其中多数还是 data URI / PNG）。
要让微信读书弹窗，就得把公式图塞进「可弹出容器」—— 但：

1. **`duokan-footnote` 的扩展开关只认 `alt` 文本**（附加说明 6）：
   `<img class="duokan-footnote" alt="文本" src="note.png"/>` ——
   弹的是 **`alt` 文本**，不是**另一个元素**。公式图没法作为 `alt`。
2. **标准 `epub:type="footnote"` 要求目标节点是文本块**，不是图片容器。
3. **Kovid（Calibre 作者）的定性**（同一 issue）：
   「阅读器只支持 EPUB 规范里**官方那一种**弹窗 + 按 CSS 样式/链接目标启发式识别；
   多看这种私有标记是**小众格式、无规范依据**，不值得为它做检测。」→
   `Won't Fix`。这说明**弹窗识别本质是「文本 → 弹出」**，不是「任意元素 → 弹出」。
4. **「点一下弹窗、再点一下跳转」的两段式交互**：需要 reader 支持
   「首次点击 → 呈现容器内容」，再把**同一个锚点**二次点击解释为跳转 ——
   这是**阅读器内部行为**，EPUB 里没有对应的书写方式。作者无法表达
   「第一下别跳」。**做不到。**

#### ④ 一个**能**做到的近似（如果用户仍想要）

把公式的**编号 + 公式图**做成一个「多看的弹窗注」形式 —— 代价与收益：

* 需要在**章末**为每条被引用的公式建一个 `<li class="duokan-footnote-item" id="df-N">`
  容器，把**公式图**放进去（比注条目重，图有 1745 张）；
* 正文引用从 `<a class="eqref">` 改成 `<img class="duokan-footnote" alt="文本">`，
  但 `alt` 只能是**文本** → 弹窗只能显示**编号文本**（`(1.32)`），
  **显示不了公式本身** —— 等于「点了弹个框告诉你编号是 1.32」，无意义。
* 结论：**投入大、效果差**，不值得做。

#### ⑤ 最终建议（保持现状）

* **公式引用就保持「锚点跳转」**。这是标准 EPUB 行为，微信读书/iBooks/Kobo/多看
  全部一致支持，且公式图**就是**跳转目标，跳过去看得最清楚。
* 注释的弹窗**已经做成了**（`duokan-footnote` + `qqreader-footnote` 双保险），
  那是对的 —— 因为注释天然是「章末有一份文本」。
* 两者**不应该统一**：一个跳到一个弹，恰恰是**内容形态**决定的，不是实现偷懒。

#### ⑥ 新增认知（写进 §0 候选）

**「能不能弹窗」由「弹窗内容是不是一份独立文本」决定，与标记写法无关。**
判断一种内容能否弹窗，先问：**它有没有一份可以脱离正文流存在的文本副本？**
有（注释）→ 可弹；无（公式图）→ 只能跳。

### §6.39 §1.5 「Implication / 蕴涵关系 / 命题」错位的**完整归因**（2026-09-18 23:xx，**判定：不易修，暂缓**）

#### ③ 源结构（干净，问题全在流水线）

| | 英文原版（`OEBPS/10_Chapter01.html`） | 中文（`prob_zh.md`） |
|---|---|---|
| | `[77] heading 'Implication'` | `[83] para '蕴涵关系'` |
| | `[78] para 'The proposition'` | `[84] para '命题'` |
| | `[79] figure (1.14)` | `[85] formula (1.14)` |
| | `[80] para 'to be read as…'` | `[86] para '读作 "A 蕴涵 B"…'` |
| | `[82] heading 'A tricky point'` | `[88] para '陷阱'` |

**关键**：英文原版里 `The proposition` 是**普通段（para）**，不是标题。
⇒ **`命题` 是「The proposition」的正文译文，本来就不该是标题。**
（代码里早先写的「宁可漏，不可误伤『陷阱』『命题』这类 2 字合法标题」——
**该假设是错的**：`陷阱`/`蕴涵关系` 对应英文侧的真 heading，`命题` 对应的
英文侧是 para。）

#### ④ 根因（`BIL_DBG_HEADS=1` 实测 dump）

```
en_heads_at = [(13, 'Implication'), (16, 'A tricky point')]
zh_heads_at = [(14, '蕴涵关系')]          ← ⚠ 应为 (13, '蕴涵关系')
[after] pair[13] en=[] zh=[13] → pair[14] en=[13] zh=[]
```

两条独立缺陷：

1. **`蕴涵关系` 标题位置 off-by-one**：注册进 `zh_heads_at` 的下标是 **14**，
   但它的真实 zh 段下标是 **13**（`Implication` 在 en 13，两侧应同相位）。
   于是渲染层按 14 输出 → 中文标题掉到公式 (1.14) **之后**。
   出处：`pipeline._extract_zh_titles` 用 `p.zh[0]` 登记（第 1289 行），
   而该函数**在 refine 之后又跑一遍**（第 720 行）—— refine 把 pair 重排过，
   `p.zh[0]` 已经不是标题段自己的下标了。

2. **`命题` 被误提升为 h4**：`_extract_zh_titles` 的守卫
   （第 1275 行：`j != p.zh[0] or len(p.zh) < 2` → 跳过）在 refine **前**成立，
   但 refine **后** pair 结构变了（`pair[14] en=[13] zh=[14]` → zh 只剩一项），
   守卫失效 → `命题`（title-like：2 字、无标点、100% CJK）被当标题摘出。
   `[after]` dump 里 `pair[14] zh=[]` 就是它被摘走的实证。

#### ⑤ 为什么「不易修」（判定）

* 这不是一个判据错误，而是**「标题摘取」与「refine 重排」的时序耦合** ——
  refine 会改变 pair 的相位，而 `_extract_zh_titles` 依赖「摘取时刻的 pair 形态」
  来定位标题。要修好，必须让摘取**只用与 pair 形态无关的信号**
  （如「本段是否 title-like **且** 英文侧同位置有 heading」），
  而这正是 §6.36 给 zh-only 分支刚加的 `en_heads_at` 判据 ——
  **把它推广到 `_extract_zh_titles` 与渲染层 `_looks_like_title` 两条路径**
  才可能根治。属于**结构性改动**，牵动标题/目录/单语版删除逻辑。
* 收益面窄：全书同类错位目前**只有 §1.5 一处**（`命题`）+
  §1.5 的 `蕴涵关系` 相位。为 1 处改动去动标题摘取的核心时序，**风险 > 收益**。
* ⇒ **按用户「看一下容易修就修，不容易就算」的授权：判定为「不容易」，暂缓。**
  记入 §3 队列（作为「标题摘取与 refine 时序解耦」整体任务的一部分），
  **不在本轮动**。

#### ⑥ 留一个低风险的可选修法（若将来只想治这一处）

渲染层 `_title_ish` 分支已经用 `en_heads_at` 判过真伪（§6.36）；
**同样一条判据可以再加到渲染层的 `_looks_like_title(_zplain, _eplain)` 提升点**
（`build.py:1557`）：如果英文侧 `_eplain` **不是** heading（`en_heads_at`
里没有对应项）、且英文该段是**句首小写起的散文**，则不提升为标题。
—— 这条只影响渲染、不碰 pipeline 时序，**改动面小**；
但需要先确认它对全书 374 个双语标题**零误伤**才能落地（需一轮 A/B 验收）。
**未做，留作候选。**
