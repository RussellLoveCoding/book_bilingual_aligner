## 4. 踩过的坑（别重蹈）

1. **指标好 ≠ 内容对**。ML 曾挂着假中文，`dbg_bookscan` 照样报「缺中文 0」。
2. **产物是哪条路建的，靠产物指纹不看记忆**：
   `grep -o 'class="pair"><p class="[a-z]*' <成品.html> | head -3`
   → `en` 在前 = unified，`zh` 在前 = legacy。
3. **先验尺再信数**。本轮 3 次事故都是「尺子自己错」：
   ① 编号被标记空格切断；② 图注信号没做方向区分；
   ③ 拿**自己臆想的译文**去源书检索（0 命中就误判「源书没有」）。
   **检索词必须来自结构性标记（公式号/示例号），不能来自猜的译文。**
4. **Windows → WSL 传参会吃掉反斜杠/竖线/heredoc**。
   `Figure\s+1-2` → `Figures+1-2`；`-c 'python - <<EOF'` 直接语法错。
   **只能写真实 .py 文件再调 `tools/_run.sh`**。
5. **Git Bash 的 `pwd` 给 `/c/...`，原生 Python 打不开** —— 交给 Python 的路径
   必须走 `pwd -W` 的 `C:/...` 形态。
6. **safe-delete 的两个坑**（清理 `diag/` 时）：
   - 一次传 >8 个路径 → `BULK_GUARD_ERROR`，**一个都不删**。分批 ≤8 或 for 循环逐个删。
   - `[ -e path ]` 在 guard 报错时**误判「已删」**（实际还在）→ 验证用 `ls`。
   - `rm -rf <目录>` 走 genie-trash 可能 fail-closed → 先 `rm -f` 删内容再 `rmdir`。
7. **判断「某功能有没有被瞎改」的正确姿势**（本轮实战）：
   - `git log -S "<关键词>"` 找引入点；`git log --oneline -- <文件>` 看谁碰过；
   - 对可疑 commit **亲眼看 diff** —— commit message 里出现关键词 ≠ 改了代码
     （`fbd979e` 的 message 提到 `apply_error_repair`，实际只删了 23 行注释）；
   - 终极验证：用 Python **按缩进切出函数体**再 diff（别用 `sed` 到下一个 `def`，
     会把模块级常量一起卷进来造成假差异）。
