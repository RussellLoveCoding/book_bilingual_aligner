# 统一架构（沉浸式翻译式同构插入）—— 设计与验收方案

> 分支：`feat/unified-immersive`
> 日期：2026-09-19
> 定调来源：用户 2026-09-18 原话（见 `docs/HANDOFF.md` §3 第 13 项）
> ——「最好像是沉浸式翻译插件一样，基本上就是**原来什么格式，翻译出来就是
> 什么格式**，**译文仅仅是塞进去接着的译文**，这是一开头就是这样的设计。」

---

## 0. 一句话

**把「英文骨架 + 中文块」的双轨重建，换成「英文原版 DOM 原样保留 + 译文作为
兄弟节点就地插入」。**

---

## 1. 现状（双轨）为什么会烂

当前 `build.py` 的发射模型：

```
英文块对象 ──┐
             ├─→ _reorder_pairs() ─→ 各自发射 <p class="en"> / <p class="zh">
中文块对象 ──┘                          ↓
                                  包进 <div class="pair">
```

实测（`diag/ml_trial4`，205 pair）DOM 次序分布：

| 形态 | 数量 |
|---|---|
| `ZH -> EN` | **166** |
| `ZH -> EN -> figure` | 15 |
| `ZH -> LABEL -> EN` | 11 |
| 其它（多 ZH / 多 EN 交错） | 13 |

**问题一：中文在前、英文在后。** 用户截图 2/3 明确要求「英文和中文紧挨着，
一个黄色方框包含两个段落，**Note 在上面**」。现在是 `ZH -> LABEL -> EN`：
标签卡在中间，且中文在上。**正确次序应为 `LABEL -> ZH -> EN`**，
或按沉浸式翻译的「英文骨架 + 译文插入」则为 `EN -> ZH`（标签跟英文走）。

**问题二：每加一种元素类型，要写两套发射代码。** 双轨路线的必然结果 ——
标题、题注、公式、注、脚注、代码块、提示框…每一种都要单独回答
「英文怎么发 / 中文怎么发 / 谁先谁后」。HANDOFF §6.35~§6.36 那一长串
「某类元素漏了侧别 token / 次序反了 / 没进扫描范围」全是这么来的。

**问题三：版式靠「搬运」。** 英文原版的缩进、行距、编号位置、缩进层级，
全都要在重建时**人工再实现一遍**，于是永远有漏。

---

## 2. 关键发现：英文侧**本来就是原样**的

读 `build.py:1631`：

```python
_h = _rewrite(_b.html, n_notes, prefix, note_texts)   # 只改脚注锚点
if _b.type != "code":
    _h = _en_math(_h)                                 # 只渲染公式
_h = _inline_img_src(_h, res, prefix)                 # 只换图片 src
_segs.append(f'<{_t} class="{_c}">{_h}</{_t}>')
```

`_rewrite()` 全文只做一件事：把脚注引用改成指向本章注释区。
**英文正文的 HTML 是逐字节来自源 epub 的**（`_b.html`）—— 斜体、粗体、
行内代码、pagebreak、原版 class 全在原样搬运。

⇒ **英文骨架的保真度已经是 100%，不需要重建。**
坏的只是**外面多包了一层我们自己的 `<p class="en">`**，
以及**中文被当成平级块插进来**。

这条发现把「伤筋痛骨的大重写」（HANDOFF 的悲观估计）降级为
**一次受控的发射层改造**。

## 3. 目标架构

### 3.1 节点模型

对每一对 `(en_block, zh_block)`：

```
[原文]  <p class="en en_original" ...>原始 HTML 逐字节</p>
[译文]  <div class="bil-zh" data-bil="zh">中文 HTML</div>
```

**译文作为原文的兄弟节点、紧接其后插入。** 原文节点**一个字都不改**
（除脚注锚点/公式/图片 src 这三项必要的引用重写）。

### 3.2 与沉浸式翻译的对照

| 概念 | 沉浸式翻译 | 本项目 |
|---|---|---|
| 原文容器 | `immersive-translate-target-wrapper` | 不加容器，**原文节点本身** |
| 译文容器（块级） | `...-translation-block-wrapper` | `<div class="bil-zh">` |
| 译文容器（行内） | `...-translation-inline-wrapper` | `<span class="bil-zh-inline">` |
| 译文文本 | `...-target-inner` | 容器本身 |
| 位置 | `imt-trans-position="after"` | 恒 `after` |
| 显示模式 | `imt-state="dual\|translation\|source"` | 同上（纯 CSS，无 JS） |
| 排除 | `[translate=no]` / `script/style/svg/math` | 代码块/公式图单独处理 |

我们**刻意简化**：不加 wrapper（原文就是容器），因为 epub 阅读器对
多层嵌套的兼容性参差；两个 class 足够。

### 3.3 元素类型 × 发射规则（**一张表，不是两套代码**）

| 元素 | 原文侧 | 译文侧 |
|---|---|---|
| 普通段 | 原样 `<p>` | `<div class="bil-zh">` |
| 标题 | 原样 `<h1..h6>` | 紧跟其后的 `<div class="bil-zh bil-head">` |
| 代码块 | 原样 `<pre>` | **不插入**（用户明确要求代码不译） |
| 公式 | 原样 `<figure>` / 表格 | **不插入** |
| 图片 | 原样 `<figure>` | **不插入** |
| 提示框 `Note` | 原样容器 | 见 §3.4 |
| 列表项 | 原样 `<li>` | `<span class="bil-zh-inline">`（行内，不进新行） |
| 脚注 | 原样 `<p class="fn">` | 紧跟其后 |

**核心收益**：译文侧永远只有**一个**发射路径（「插到原文后面」），
不再有「英文怎么发 / 中文怎么发」的配对问题。

### 3.4 提示框（用户截图 #2 的直接诉求）

英文原版：

```html
<div data-type="note"><h6>Note</h6><p>正文…</p></div>
```

目标输出（**标签在顶、中英各一段、同一个框**）：

```html
<div class="bil-box bil-box-note">
  <h6 class="box-label">Note</h6>
  <p class="en en_original">正文…</p>
  <div class="bil-zh">译文…</div>
</div>
```

⇒ 完全满足用户的「英文和中文紧挨着 / 一个黄色方框包含两个段落 / Note 在上面」。

## 4. 迁移策略（**增量，不推倒**）

不改 `pipeline.py`（对齐逻辑一行不动），只改 **`build.py` 的发射层**。
用一个环境变量做开关，便于**同机 A/B 对照**：

```
BIL_ARCH=legacy      # 现状双轨（默认，保证回归零变化）
BIL_ARCH=unified     # 统一架构（新）
```

理由：这样能在**同一批源书**上跑两版、逐项 diff，而不是「改完再看」。
HANDOFF 铁律 3 的教训（只看 stdout 指标会漏掉产物降级）要求这个开关。

### 5.2 门禁（改完必跑，逐项）


```bash

```

### 5.4 **人工判读**（用户强调：指标不够，必须抽样推理查看）

- 抽 30 个 pair 逐条读中英是否对应（沿用本轮 `_dbg9.py` 的做法）。
- 截图比对：同一段落在 legacy / unified 两版下的观感。
- **不只看指标**：指标一致 ≠ 产物一致（HANDOFF 铁律 3）。

### 5.5 判据：什么算「值得走这条路」

用户问的是「验证一下这条路行不行」。**成立的判据**：

1. 门禁全绿，且 `dbg_qa` 相对 legacy **不劣化**；
2. 用户点名的 6 项（错配 / Note 在顶 / 代码不译 / 代码图片公式随英文 /
   公式 6-4 归位 / 整体版式忠实英文）**逐项在样章里肉眼可验**；
3. **代码量对比**：译文侧发射路径从「每类元素一套」收敛到「一条」。
   HANDOFF 留的判据是「看还剩多少『元素类型 × 两套发射代码』」——
   收敛即是成立的证据。

**不成立的判据**：只因为「架构好看」就推全量。必须 1–3 都过。

## 6. 风险与已知坑

| 风险 | 说明 | 对策 |
|---|---|---|
| epub 阅读器兼容 | 阅读器对未知 class 一律忽略，**风险低**；但 `<div>` 套在 `<p>` 位置可能影响段距 | 用 `<div>` 而非 `<p>` 包译文，CSS 显式给 margin |
| 微信读书不执行 JS | 沿用纯 CSS 的显示模式切换 | `imt-state` 用 checkbox hack（已有先例） |
| 行内元素 | 列表项/行内代码的译文不能另起块 | 用 `<span class="bil-zh-inline">` |
| **`_V` 版本** | 若只改渲染层、不动解析/对齐，**不需要 bump** | 本轮默认不 bump；若动了 `pipeline.py` 再 bump |
| 回归污染 | 改 `build.py` 会改所有书的产物 | `BIL_ARCH` 开关 + legacy 作基线 |
